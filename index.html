Course Overview

What this course is about

Robots are everywhere, often in ways we don't notice. This course demystifies them. Students learn that no matter how complex a device looks, it comes down to connecting wires between electronic parts, programming a controller to read sensor inputs, and using that logic to drive outputs — lights, motors, sounds — without human involvement.

Over 16 weeks students progress from blinking an LED to designing their own algorithmic measurement system. The through-line is always the same: define a real-world problem, build and wire a prototype, write code, iterate with feedback, and document the whole process.

Hardware used

BBC micro:bit (v2) with expansion board, Sphero RVR (first week), L298N motor driver, Adafruit Metro RP2040 (Unit 3), breadboards, LEDs, buttons, analog/digital sensors (IR, joystick, NeoPixels, servo, temperature, light, sound), and multimeters.

Software and tools

MicroPython on the micro:bit via Mu Editor and the online editor at python.microbit.org. CircuitPython on the Metro. Desmos for graphing live sensor data. Gemini AI used throughout as a coding and iteration partner. Edpuzzle for video assignments. Custom EMW Robotics Simulator for virtual robot programming.

AI philosophy

Generative AI (Gemini, Claude, ChatGPT) is treated as a legitimate learning tool. Students use it to generate starter code, explain concepts, iterate on prototypes, and get feedback on pitches. The course teaches students to direct AI with specific prompts and to critically evaluate what it produces — not just copy-paste.

Assessment philosophy

The course uses a proficiency scale (0–4) across six standards. There is no single final exam. Instead, students accumulate evidence across projects and activities throughout the semester. Each activity targets specific standards at specific levels. Some are quick mastery checks (Level 2), others are multi-day projects (Level 3), and advanced students find opportunities for Level 4 work.

The end-of-semester grade reflects overall achievement across all six standards. Students know which standards are being assessed for every activity. Missing work is addressed through additional learning opportunities rather than zeros alone.

Unit 1 — micro:bit and Events

Weeks 0–5 · Days 1–15 · approximately 15 class sessions
Students go from zero programming experience to having a working, wired, event-driven micro:bit device they designed and built themselves. The unit establishes the foundational framing for the entire course: inputs trigger events, processors respond, outputs react — without human involvement.

Learning goals

By the end of Unit 1 students can:

  • Define what a robot is (reads inputs, controls outputs, without human involvement)
  • Identify and explain events in a MicroPython program
  • Build basic electronic circuits (LED, motor, button, breadboard)
  • Read analog and digital sensor data and graph it in Desmos
  • Wire external sensors and outputs (IR sensor, NeoPixels, servo, joystick) to the micro:bit
  • Use AI (Gemini) to generate, iterate on, and explain code
  • Document an iterative design process across multiple class days
Communication L2 Iterations L2 Hardware I/O L2–L3 Events L2–L3

Scaffolding approach

The unit opens with the Sphero RVR challenge — a fun, low-stakes way to surface the idea of command sequences (effectively: algorithms) before the word "algorithm" is introduced. Students immediately see that a program runs in sequence and doesn't adapt to the environment.

The micro:bit is then introduced as a device students can hold and program on the same day. Events are introduced through a scavenger hunt: find five events built into the micro:bit without being told what to look for. Circuits start dead-simple (light one LED) and build toward breadboard circuits and finally external sensors.

The L2 iteration task with Gemini AI scaffolds the design process explicitly: start with a prompt template, generate code, test it, explain what doesn't work, ask Gemini to improve it. This is repeated across three documented iterations before the full Project 1.

Day-by-day lesson sequence

D1Robotics Intro
Iterations
U1D1 Slides
What students do

The lesson opens with the "what is a robot?" question through a set of images — factory arm, Roomba, self-driving car, vending machine. The class lands on a working definition: reads inputs, controls outputs, without human involvement. The bulk of class is the RVR coding challenge: teams write movement commands on paper in Python-tuple format (e.g. ("W", 1.5) for "forward 1.5 seconds") and watch the robot execute them with no mid-run adjustments allowed.

Teacher notes

The challenge is designed to fail productively. Most teams over- or under-estimate timing, or forget a turn — that's the point. The robot doesn't interpret intent, it follows commands exactly. The debrief question "what would you change?" is the seed of the Iterations standard. There's also a "neat vs. messy / looks good vs. works well" discussion that frames the course's quality philosophy from day one.

D2RVR Debrief & micro:bit Intro
All standards introduced
U1D2 Slides
What students do

Brief survey, then RVR debrief connecting team results back to the robot definition. The Etch-a-Sketch analogy: the teacher draws a circle manually, then asks what motor commands a robot would need to do the same. Proficiency scales introduced. Students get their micro:bits, connect via USB, and open python.microbit.org. Mu Editor download shared.

Teacher notes

The Etch-a-Sketch analogy is worth dwelling on. A person drawing a circle uses continuous feedback and can adjust mid-stroke; a robot following commands has to get each step right in advance. This is why precision matters and why iteration exists. Keep the proficiency scale intro light here — the key point is that 3.0 is the goal and 2.0 is the foundation.

D3micro:bit Events Intro
Events
Events Catalog
What students do

Scavenger hunt: students find 5 built-in micro:bit events on their own using the online simulator, then record them in the W1-3 Events Catalog Google Doc — no hints given. Events found typically include button presses, shake, tilt, microphone level, and temperature. At the end of class, students upload their first hex file from the online editor.

Teacher notes

Events are framed here as "when/if [something happens]" rather than with a technical definition. Starting from "the micro:bit knows when this occurs" is more accessible than event-driven programming theory. The hex file upload is the first time students experience the compile-flash-test loop — watch for confusion about how to get the file onto the board, as it trips up a surprising number of students.

D4Circuit Building Part 1
HardwareEvents
What students do

L2 Events warm-up: given a few lines of code, students identify and circle the events. Then breadboard intro — row/column connections, internal structure. Build circuits 1–3: light an LED from a 3V battery, spin a motor, use a button to control a motor. Each circuit documented in the W1-5 Circuit Building Template with photos.

Teacher notes

Students often don't believe breadboard row connections until they see the internal diagram — worth showing a disassembled one. LEDs are polarized and backwards wiring is a common first error; it's a useful early debugging moment. The warm-up events analysis doubles as an informal check that D3 understanding stuck before moving into hardware.

D5Circuits Part 2 & Sensor Data
Hardware
W2-1 Slides
What students do

Complete circuits 4–6: breadboard LED with resistor, button-controlled LED, micro:bit-controlled LED via Pin 0. Then the sensor data lab: provided code reads the light sensor and button state and pipes values into a Desmos graph in real time. Students watch analog (smooth curve) and digital (step function) data appear on the same axes. The Desmos screenshot is the L1.5 submission — the first assessed piece of the course.

Teacher notes

The live Desmos graph is the clearest possible illustration of the analog/digital distinction — students see it rather than hear a definition. The lab requires the micro:bit connected via USB with the REPL open, which is a new connection mode. The W2-1 slides walk through it carefully, but plan for some students to need help with the USB setup.

D6Analog vs. Digital & Project Brainstorming
HardwareIterations
U1D6 Slides
What students do

Warm-up formalizes D5: read the temperature sensor and simulate 24-hour Santiago data in Desmos. The analog/digital contrast is named explicitly. Then the unit's first major creative step: students use a Gemini prompt template to brainstorm a real-world problem and generate AI starter code. The template tells students exactly what context to give Gemini — grade level, platform, code format — so the output is actually usable.

Teacher notes

The Gemini prompt template is not optional scaffolding. Without it, students either get code that doesn't run in MicroPython or responses too vague to use. Watch the brainstorm closely: the constraint "something you could build with sensors the micro:bit already has" is important. Students often propose ideas requiring GPS or a camera. Redirect toward light, temperature, sound, buttons, and the accelerometer.

D7L2 Iterations with AI (due)
Iterations L2Communication L2
Iteration Example
What students do

Full work day. Students iterate starter code through at least 3 versions using the W3-2 micro:bit Prototyping Template. Each iteration documents the current code, what was tested, what didn't work, the exact Gemini prompt used, and the new code. L2 Iterations task due end of class.

Teacher notes

The L2 standard isn't just "show three drafts" — it requires explaining what changed and why. The teacher's own iteration example (W3-3) is worth walking through at the start of class: it shows the teacher's code didn't work first either, and that articulating a problem clearly to Gemini produces a better result. The parallel between precise prompting and precise debugging is worth naming explicitly.

D8Multimeter & Breadboard Deep Dive
Hardware
U1D8 Slides
What students do

Introduce the micro:bit expansion board. Systematic multimeter exploration guided by an 11-step worksheet: use the continuity setting to trace which breadboard columns connect to which GPIO pins, then the voltage setting to measure battery vs. USB power and Pin 0 HIGH vs. LOW state.

Teacher notes

This is a genuine engineering skills lesson. The key shift: students stop guessing whether a connection works and start measuring it. Using the multimeter as a debugging tool — not just a measurement instrument — changes how students troubleshoot circuits for the rest of the course. The worksheet keeps the exploration systematic rather than random.

D9Breadboard Tasks Continued
Hardware
W4-1 Slides
What students do

Using the expansion board from D8: wire an external LED to Pin 0 via breadboard (resistor required). Write code to turn it on and off with button presses. Explore the micro:bit schematic to understand which GPIO pins support which functions. Voltage readings with battery pack vs. USB.

Teacher notes

A key micro:bit detail surfaces here: Pin 0 must be declared as output in code even when the circuit is correctly wired. The physical connection alone isn't enough. Students who skip this step have a working circuit that does nothing — a useful, low-stakes debugging moment before Project 1.

D10Events Code Analysis (L3)
Events L3
What students do

Warm-up: given a wiring diagram and a joystick module, wire the joystick to the expansion board as an analog input. Main task: L3 events analysis — students receive a micro:bit program more complex than anything they've written, with multiple concurrent event handlers, and must identify each one and explain exactly what it does and when it fires.

Teacher notes

The jump from D3 (find events in simple code) to this L3 task is significant. The L3 program includes button combinations, accelerometer conditions, and possibly a background loop — multiple concurrent structures. Students who struggle often conflate "event handler" with "function." Remind them: this task is as much a code reading problem as a coding one.

D11External Circuits
Hardware L3
W5-1 Slides
What students do

Systematically work through four external components: joystick (analog input), IR sensor (digital input), NeoPixel strip (digital output), servo motor (PWM output). Sample code provided for each. Students wire, run, and modify each to confirm they understand the behavior. Design task at the end: use at least one component in a novel way.

Teacher notes

This lesson is intentionally broad rather than deep. The goal is that students can make informed hardware choices for Project 1, not that they master every component. Power supply considerations come up here — some components need 5V, others work at 3.3V. The NeoPixel strip requires correct polarity on all three pins. The servo requires thinking in angles, not on/off.

D12Project 1 Launch: Bit by Bit
Wiring L3Iterations L3Events L3Communication
What students do

Event handler review warm-up. Project 1 introduced: design a micro:bit device using external components to solve a real problem, solo or in pairs. Students open the Google Slides template — it requires wiring diagrams, photos of each build version, Gemini interaction logs, and event documentation — and write their initial problem description and requirements.

Teacher notes

The critical teacher intervention: redirecting vague ideas to specific, achievable ones. "A smart home" needs to become "a lamp that turns on when the room gets dark." Documentation must start today — photos taken each day, not reconstructed at the end. All three standards (Wiring, Iterations, Events) must be evidenced in the slides; students can't rely on just one.

D13–D15Project 1 Work Days
Wiring L3Iterations L3Events L3
Exemplar L3 Doc
What students do

Three full build days. Students design, wire, code, debug, iterate, and document. Each day ends with a reflection slide added to the presentation. Teacher circulates for the observational wiring assessment.

Teacher notes

The most common failure mode: students get something working on Day 1 and stop genuinely iterating. Push them — what breaks this? What could go wrong for a different user? How would you improve it with another week? The iteration requirement is about showing a design process, not a progression of drafts. Do wiring observations before the final day, since students sometimes disassemble their circuit at the end.

Unit 2 — Functions and Modular Code

Weeks 6–10 · Days 16–27 · approximately 12 class sessions
Students learn to break complex programs into reusable, testable functions. The unit moves through three escalating contexts: functions on micro:bit with Mu Editor, motor driver control (wiring a new piece of hardware and writing functions to drive it), and a custom-built virtual robot simulator where students implement a task using well-structured functions. Communication (design reports and pitches) is formally introduced this unit.

Learning goals

By the end of Unit 2 students can:

  • Identify function inputs (parameters) and outputs (return values) in Python code
  • Call functions with correct syntax and a variety of parameter types
  • Write and test functions with no parameters, parameters only, and parameters + return values
  • Decompose a larger project into function-sized pieces
  • Wire and control an L298N motor driver using a micro:bit
  • Give a 1-minute pitch explaining a problem and current prototype state
  • Write a design/status report documenting their current solution
  • Program the virtual robot simulator using task functions
Functions L2–L3 Communication L2–L3 Hardware L3 Iterations L3

Scaffolding approach

The unit opens with pitches — students give a 1-minute verbal status report on Project 1 to Gemini, which provides critical feedback. This introduces the Communication standard explicitly and connects it to work students already did.

Functions are introduced through Edpuzzle videos and a Gemini conversation using a prompt template. Then Mu Editor (desktop Python) is used to write and test functions in isolation before putting them on the micro:bit. This is intentional: decoupling the hardware from the concept prevents students from conflating "the micro:bit is broken" with "my function is broken."

The motor driver wiring task is introduced cold — students get hardware and a website guide, and use Gemini to navigate extending the code. The virtual robot simulator then gives a completely controlled environment for demonstrating function design.

Communication L2

What students do

Class sets up trays, installs Mu Editor. Main activity: 1-minute pitch to Gemini. The slide shows the exact prompt — students paste the L2 Communication criteria into Gemini, then type their verbal pitch and ask for critical feedback. Teacher notes

This is one of the more creative AI uses in the course. Students aren't asking Gemini to write their pitch — they're asking it to evaluate their pitch against a specific standard. The feedback tends to be sharp: Gemini notices when a pitch is all future plans and no current-state description. A design report talks about what exists now, not what the student hopes to build. Most students are surprised by how direct the feedback is.

Two Edpuzzle video assignments on functions with embedded questions. Videos cover all three function types: no parameters, parameters only, parameters with return values. A Gemini conversation on function inputs/outputs follows the videos. L1.5 grade based on completion.

Edpuzzle lets the teacher embed questions at key moments in the video — "what will this function return?" — without a lecture. The Gemini conversation immediately after matters: it forces students to articulate what they just watched before they've had a chance to forget it. Keep the conversation focused on identification: given this function definition, what are the inputs and what does it return?

The video format is deliberate — this is the most complex single coding task in Unit 2 and students need to be able to pause and rewind. Motor Driver Website
What students do

Unit 3 — Metro and Algorithms

Weeks 11–16 · Days 28–43 · approximately 16 class sessions
A new hardware platform (Adafruit Metro RP2040 with CircuitPython) and a new conceptual focus: algorithms. Students learn to design solutions before coding them — through flowcharts and pseudocode — and apply that thinking to a final design challenge where they build a Metro-based system that measures or classifies something in the real world. The unit culminates in a hackathon and final assessment week.

Learning goals

By the end of Unit 3 students can:

  • Install CircuitPython on the Adafruit Metro RP2040 and run basic programs
  • Wire sensors and motors to the Metro and adapt example code
  • Explain what an algorithm is and identify examples (Towers of Hanoi, self-driving car logic)
  • Draw flowcharts using standard symbols and notation
  • Write pseudocode for a multi-step program
  • Use AI (Gemini) to develop and refine an algorithm, then document the design with flowcharts
  • Design and build an original Metro-based algorithm design project
  • Pitch a project at a hackathon and submit final evidence for chosen standards
Algorithms L2–L4 Hardware L3 Iterations L3 Communication L4

Scaffolding approach

The transition to the Metro is managed carefully. Students set up CircuitPython on Day 1 of the unit following a guide, and the teacher's custom demo website (evanweinberg.com/robotics/tetrix_metro/) walks them through motor control step by step. The familiar concept of motor control from the motor driver task gives them an anchor.

Algorithms are introduced concretely with Towers of Hanoi and a self-driving car prompt — both force students to articulate step-by-step decision logic before any code is written. The NYT "Are You Smarter than AI?" puzzle is used as a warmup to surface the idea that intelligence is often about following systematic rules.

The algorithm design project uses a Gemini conversation scaffold: a prompt template guides students through defining a measurement challenge, developing the algorithm interactively with AI, and then drawing a flowchart that the AI validates. The conversation summary becomes the documentation artifact.

D29Metro Motor Demo Website
Hardware L3
Metro Motor Demo
What students do

Work through the teacher's custom motor control website. Wire the Tetrix motor to the Metro. Run example code, modify parameters, and observe results. The site walks through motor wiring, encoder wiring, basic motion, and reading encoder values.

Teacher notes

There are no slides for this day — the website is the entire lesson. It was built specifically for this hardware configuration so the pin numbers, code examples, and wiring diagrams all match exactly what students have in front of them. The encoder is a new concept: a sensor inside the motor that counts rotations, giving the motor awareness of its own position. This sets up the motor challenge on D30.

D30Are You Smarter than AI? + Algorithms Intro
Algorithms
W11-4 Slides
What students do

Warm-up: NYT "Are You Smarter than AI?" puzzle — students try to beat an AI at a task requiring systematic rule-following. Towers of Hanoi: solve for 3, 4, then 5 disks, then articulate the algorithm in plain language. Self-driving car discussion: what rules would a car need to follow to drive itself? Metro Motor Challenge introduced: program the motor to move to a specific encoder position and stop.

Teacher notes

Towers of Hanoi is often students' first encounter with a problem where the algorithm IS the solution — there's no "try it and see." The NYT puzzle surfaces the idea that what looks like intelligence is often systematic rule-following. Both feed into the key framing for Unit 3: a good algorithm is one you could hand to someone with no context and they could execute it exactly.

D31Metro Motor Challenge (L3)
Iterations L3Hardware L3
What students do

Build and iterate on the motor challenge: program the Metro to move to a target encoder position accurately. Document at least 3 iterations in the template, with each showing code changes and test results. Teacher's own iteration document shared as a model.

Teacher notes

Sharing the teacher's iteration document is one of the strongest pedagogical moves in the course. It shows: the teacher's first version didn't work, the teacher had to debug, the teacher documented what went wrong. Students who think good work means getting it right first need to see the person assessing them doing it the way the standard requires.

D32–D33Flowcharts and Pseudocode
Algorithms L2
What students do

D32: formal introduction to flowchart symbols (ovals, rectangles, diamonds, parallelograms). Students use a Gemini prompt to analyze their own previous code and generate a flowchart. D33: draw the flowchart by hand or digitally, then submit to Gemini for feedback on accuracy. The U3D8 handout guides the analysis.

Teacher notes

Students often conflate pseudocode with commented code. Pseudocode is language-independent logic — no Python syntax, no indentation. Watch for students who paste Gemini's flowchart output without really processing it. The goal is that a student can trace their own program logic through the diagram they produced, not just that they've submitted a diagram.

D35Algorithms Case Study — Reaction Tester
AlgorithmsHardware
What students do

Warm-up discussion: how would you measure reaction time with buttons and LEDs? Students build the reaction tester — Metro, two buttons, one LED — and trace the algorithm structure: set state → wait for event → record time → calculate → display. Design Challenge introduced: build a Metro-based system that measures something otherwise hard to see or track.

Teacher notes

The reaction tester is useful because the algorithm has a specific, reusable pattern. Once students see trigger → capture → calculate → display, they can map their own design challenge onto it. The transition from the case study to the design challenge should feel like: here is the template, now what's your version of each step?

D36L3 Algorithm Design with Gemini
Algorithms L3
What students do

Students use the full Gemini algorithm design prompt: define the measurement challenge, describe the hardware, explain what triggers the measurement, and ask Gemini to guide the algorithm design through leading questions. After the conversation, students draw a flowchart summarizing the algorithm. This conversation and flowchart together are the L3 assessment artifact.

Teacher notes

The prompt asks Gemini to ask questions rather than provide answers, making it a Socratic partner rather than a code generator. This is the most carefully designed AI interaction in the course. Watch for students who let Gemini jump straight to code — they're missing the point of the L3 standard, which is about designing the algorithm before writing it.

What students do

Full build day: implement the algorithm designed in D36 on the Metro, iterate, debug, and document. Students should be working from the flowchart they drew — if the algorithm is wrong, the code will be wrong.

Students who designed a vague algorithm in D36 will hit a wall here. That's actually useful — it surfaces the importance of the design-before-code sequence. Push students back to their flowchart rather than letting them improvise. The project template should have new photos and iteration notes by end of class.

Proficiency Standards
This course uses Nido de Aguilas's proficiency scale (0–4). Score 3.0 is the priority standard — the learning goal. Score 2.0 covers foundational vocabulary and simpler processes. Score 4.0 requires in-depth inference, transfer, and application. Students earn half-point scores (1.5, 2.5, 3.5) for partial progress between whole levels.

Communication [Documentation]

4.0Exceeds standard
Documentation is detailed enough that another student could replicate the design. Communicates elements of the design in a particularly engaging or innovative way.
3.0Meets standard
Communicates a detailed explanation of a design problem, the state of the proposed solution, and its features. Structures documentation logically from one stage to the next. Uses design principles and appropriate text, images, and video to communicate with an audience.
2.0Approaching standard
Shows elements of the design process using text, visuals, and graphic design principles. Identifies the problem and proposed solution at a point in time. Explains how a design meets the requirements of a problem.

Prototypes & Iterations [Design Process]

4.0Exceeds standard
Creates a program or prototype that helps solve a problem for someone else in the school. Shows others how to test and improve their prototypes. Finds creative ways to make the program do more than what was asked.
3.0Meets standard
Creates and tests multiple versions of a program/prototype that solves a problem, explaining personal design choices. Analyzes specific challenges in each version and how to address them. Demonstrates how testing and feedback leads to changes.
2.0Approaching standard
Modifies existing code to create a basic working prototype. Tests a prototype against given requirements. Explains basic changes between versions.

Hardware Inputs & Outputs [Technology Use]

4.0Exceeds standard
Builds systems that use multiple sensor types and outputs together. Finds creative new ways to use the hardware. Adds features that help find and fix hardware problems.
3.0Meets standard
Connects sensors and outputs to a control board and demonstrates that outputs correctly respond to inputs. Correctly implements inputs and outputs in code within a larger program. Troubleshoots connections between power, sensors, and control boards.
2.0Approaching standard
Picks appropriate sensors (analog/digital) and outputs for a project and connects them correctly. Follows diagrams to wire a circuit. Changes example code to read inputs and set outputs.

Responding to Events [Technology Use]

4.0Exceeds standard
Makes programs that handle many different events simultaneously. Creates helpful ways to show what events are happening. Adds special code to handle unexpected problems or errors.
3.0Meets standard
Writes code that responds correctly when buttons are pressed or sensors activated. Makes programs that handle different types of events. Shows clearly when events are detected and what the program does in response.
2.0Approaching standard
Finds and names the different events in example programs. Explains what happens when different events occur. Makes simple changes to how programs respond to events.

Functions & Modular Code [Technology Use]

4.0Exceeds standard
Reorganizes complex code to make it clearer and more efficient. Creates a collection of functions that can be used in different projects. Uses advanced ways to make functions work together.
3.0Meets standard
Designs and uses functions with appropriate inputs and outputs (parameters and return values). Breaks down a personal project into smaller, function-sized pieces. Documents functions with examples showing their specific use (purpose, parameters, return values).
2.0Approaching standard
Identifies function inputs, outputs, and basic operations. Demonstrates proper function calling syntax with different parameter types. Tests functions using provided test cases.

Planning & Algorithms [Technology Use]

4.0Exceeds standard
Creates especially clear and efficient solutions. Uses advanced ways to control program flow. Designs solutions that can be applied to similar problems.
3.0Meets standard
Creates detailed flowcharts and pseudocode to plan program logic. Implements complex control structures using compound boolean operators and switch/case statements. Designs and documents algorithms that solve multi-step problems.
2.0Approaching standard
Draws simple flowcharts to show how a program will work. Follows and adjusts existing code to solve a problem. Uses and adjusts basic program controls (if/then, loops) from example code.

About the instructor

Evan Weinberg teaches at Nido de Aguilas International School in Santiago, Chile. He got into robotics through a university course building and programming LEGO robots, and has spent years leading high school robotics competition teams. He builds custom web tools for his students, including the motor driver guide, Metro demo site, and the robotics simulator linked above.

His teaching approach centers on real problems, honest iteration (including showing students his own documented debugging process), and treating AI as a legitimate learning partner rather than a shortcut to avoid.
